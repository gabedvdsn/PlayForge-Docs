Authored or written

Most of a game made with PlayForge is assets:

  • They're authored in The Forge, Window → PlayForge → The Forge.
  • They're kept in a Forge Project, under Assets/PlayForge/<project>.
  • Code plays them, and adds kinds of the game's own that their pickers then offer.
Authored in The Forge Written in code
Attributes and attribute sets Scripts that play the assets: casting on input, applying an effect on a hit, reading attributes for UI
Entities (EntityIdentity) A game's own components, workers, ability tasks, targeting tasks, scalers, value stages, cue handlers and validation rules (Extending PlayForge)
Effects, among them every cost and cooldown Processes and task sequences (Processes, Task Sequences)
Abilities: their targeting, stages, tasks and checks A game's own data in a save (Saving and Loading)
Items, value pipelines, scalers, templates and requirement templates Tests, with the test kit (Testing Your Content)
Tags, in the Tags view, and the workers on each asset Tags a game names in code (Tags)

So:

  • Asked to make an asset, give the steps in The Forge, with each label as the editor shows it; the guides name them. Make it in code only when asked to, as Making assets in code shows.
  • Never write or edit an .asset file's YAML. An asset's components, tasks and workers are [SerializeReference] lists of polymorphic kinds, which a hand edit easily breaks.
  • A kind of the game's own needs a public constructor that takes nothing, and [Serializable]. Nothing registers it: the pickers find it by its base (Extending PlayForge: Before you start).
