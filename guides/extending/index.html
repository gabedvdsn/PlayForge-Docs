Extending PlayForge

PlayForge's rules are kinds a designer picks in an inspector: components, workers, tasks, scalers, conditions, stages, cue handlers and more. A game adds its own by writing a class of the same base. The editor finds the class, its picker offers it beside PlayForge's own, and it runs where they run, handed what they're handed. This guide covers each place a game's code plugs in: the base to derive from, the hooks it overrides and when each is called, how the kind reaches the inspector, what it's handed, a complete example, and the traps.

Code that only uses PlayForge, as a script that casts an ability or reads an attribute, needs none of this. The kinds here plug into what Workers, Scalers, Processes and Task Sequences explain.

In this guide

  • Before you start: This section covers what every kind of a game's own shares: the assembly it lives in, how the editor finds it, how its picker names and files it, how its fields show, where it keeps what it counts, and how it's renamed.
  • Components: A component is a feature an asset carries in its Components section: an effect's, an ability's, an entity's or an item's.
  • Workers: A worker is a small rule an entity holds in a worker group, or an effect holds in its Workers, that reacts to what happens: an attribute's change, a hit it deals, its tags, its frame's events, an effect's life.
  • Deferred actions: A deferred action is a piece of work queued to an entity that runs at its end of frame, by priority: what deferred workers return, and what any code queues with entity.GetActionQueue().Enqueue(action).
  • Ability tasks: An ability task is a step of an ability's stage: it's picked in a stage's Tasks, runs with the stage, and is handed the activation's data.
  • Targeting tasks: A targeting task picks what an activation acts on before its stages run: it's the ability's Targeting, one task, run as the activation starts.
  • Sequence tasks, injections and stage policies: A task sequence runs stages of tasks, built in code with TaskSequenceBuilder (Task Sequences).
  • Processes: A process is anything that runs over time under ProcessControl: a MonoBehaviour or a plain C# object stepped from Unity's player loop.
  • Scalers, number kinds and conditions: A number field's Kind says how its number is worked out, and a Conditional's or a rule's condition says whether it holds.
  • Value stages: A value stage reshapes a hit's value on its way to its attribute, one of a Value Pipeline's Stages, which an effect's impact names as its Pipeline (Value Pipelines: Stages).
  • Cue handlers: A cue handler plays feedback, a shake, a sound, an animation, at an effect's, an ability's, an entity's or an item's moments, or where a cue tag routes.
  • Entity services: An entity service is an object of a game's own each entity keeps as it runs, made the first time it's asked for and stepped by the entity's own time: a combo count, a cooldown of the game's own, a respawn's wait.
  • Validation rules: A validation rule refuses an ability's activation: one of the ability's Caster Checks, asked of the caster, or its Target Checks, asked of the target once its targeting has picked one.
  • Smaller kinds: This section covers the smaller kinds a game picks in one field each: where an entity respawns, how charges come back, what a purge takes, how a modifier changes an effect, a Local Data value's type, and the clock a run…
  • A game's own objects: PlayForge asks a game's own objects for a few things through interfaces: turning, moving, shaking the camera, and a pooled cue's comings and goings.
  • Readers: A reader is a MonoBehaviour process that shows an entity's state, a bar or a counter: AbstractReader, a LazyMonoProcess, which Assign(gas) gives its entity.
  • Time, randomness and input: PlayForge reads its time, its random numbers and its pointer through sources a game can replace, so a game can run it on a fixed step, repeat its rolls, or aim with a gamepad.
  • Saving a game's own data: A ForgeSnapshot holds what PlayForge saves of an entity, and nothing of a game's own: a game saves its own data beside it.
  • Tags in code: A game's code names tags for its kinds to read: a data key, an event, a state its components grant.
  • The editor: A game's editor code can check PlayForge's assets, draw a base type of its own as PlayForge draws its kinds, and start new assets from its own templates.
  • Testing your extensions: PlayForge's test kit runs a game's own kinds in a world of entities stepped frame by frame, in Unity's Test Runner.
  • The Creator Lab: The Creator Lab plays a project's assets on units of its own (The Creator Lab).
