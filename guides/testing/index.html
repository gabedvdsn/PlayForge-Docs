Testing Your Content

A game's abilities, effects and items are easiest to trust when a test plays them as the game does: a burn's ticks landing over its second, a ring's armor while it's held, a cast paying its cost.

PlayForge's test kit is the assembly FarEmerald.PlayForge.Testing, in the package's TestKit folder, which a project's own tests reference. For each test, the kit:

  • brings up a live PlayForge, and steps it a frame at a time;
  • makes entities on either hub, and plays them;
  • checks afterwards what must always hold, and takes it all down again, so tests run in any order.

In this guide

  • Setting up: The kit is compiled wherever the Test Framework package (com.unity.test-framework) is installed, as the Test Framework's own test runner is.
  • A test: A test class derives from ForgeTest.
  • The world: The world makes a test's entities and assets, plays them, reads them, and controls its time, its chance and its processes.
  • What must hold: After each test that passed, the world's audit checks what must always hold
  • Allocation: AllocationProbe measures what's allocated, with the profiler's counter, as the GC's own reads 0 under Mono.
  • Traps: These are the mistakes a test most easily makes with the kit.

In the API

The types of this guide's area: AllocationMarker, AllocationProbe, EffectConfig, ForgeTest, ForgeTestWorld, FrameAllocation, FramePulse, FrameStepper, Hub, Invariants, ScriptedRandom, SteppingClock, TestAssets.
