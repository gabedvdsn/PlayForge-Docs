Testing Your Content

A game's abilities, effects and items are easiest to trust when a test plays them as the game does: a burn's ticks landing over its second, a ring's armor while it's held, a cast paying its cost. PlayForge's test kit is the assembly FarEmerald.PlayForge.Testing, in the package's TestKit folder, which a project's own tests reference. It brings up a live PlayForge for each test, steps it a frame at a time, makes entities on either hub, and plays them; and after each test it checks what must always hold, and takes it all down again, so tests run in any order.

In this guide

  • Setting up: The kit is compiled wherever the Test Framework package (com.unity.test-framework) is installed, as its own test runner is.
  • A test: A test class derives from ForgeTest, which makes a ForgeTestWorld before each test and audits and ends it after.
  • The world: Entities: World.Entity(hub, set, name) makes an entity of an attribute set on either hub, Hub.Runtime (a RuntimeGameplayAbilitySystem) or Hub.Mono (a GameplayAbilitySystem on a GameObject of its own)…
  • What must hold: After each test that passed, the world's audit lets three frames settle, ends what the test left running of what it began, and fails the test where any of these broke
  • Allocation: AllocationProbe measures what's allocated, with the profiler's counter, as the GC's own reads 0 under Mono: Measure(action) what one run allocates, MeasureEach(action, runs, warmup) the mean of many after a…
  • Traps: Step frames; never call a process's update by hand. The world's ProcessControl steps what runs, as the game's does; calling an update yourself runs it out of order and hides what the frame does.

In the API

The types of this guide's area: AllocationMarker, AllocationProbe, EffectConfig, ForgeTest, ForgeTestWorld, FrameAllocation, FramePulse, FrameStepper, Hub, Invariants, ScriptedRandom, SteppingClock, TestAssets.
