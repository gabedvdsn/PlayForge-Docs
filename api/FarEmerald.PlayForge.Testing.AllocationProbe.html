Class AllocationProbe

Namespace
FarEmerald.PlayForge.Testing

Measures allocation with Unity.Profiling.ProfilerRecorder, because the GC API returns 0 under Mono. Unity's "GC Allocated In Frame" counter reads live within a frame, so an operation is the counter's change across it. Dispose it as the test ends.

A frame takes more care, because the counter's own total for a frame is noisy: 450 to 532 bytes with nothing running, shifting at random. Sampling every player loop stage shows why. All of that lands outside the player loop, in the editor's work between frames, except 40 bytes from the test runner's coroutine tick. So a frame here is the counter's change from the player loop's first stage to its last, less that tick, measured on the same frame. A clean frame reads exactly 0, with no baseline to calibrate, and a baseline would be worse than noise: taken while the noise ran high, it would hide real allocation.

The cost is that anything allocated in a coroutine goes unmeasured with the test runner's. PlayForge's stepping runs in Update and its async work in UniTask continuations, which are measured.

Now and then a burst of a kilobyte or so landed on a few frames at random, whatever was running. It was the editor's Build Report REST service, which listens on a port of its own: where another editor holds that port, as one open beside a batch run does, it tries again about once a second on a thread of its own, and each try allocates about 4 KB, which the counter takes as the frame's. Most frames are short, so a try rarely landed in one, but among 500 entities, whose frames fill most of a second, nearly every measure took one. A probe ends those tries (FarEmerald.PlayForge.Testing.AllocationProbe.EndRestServiceRetries()). Other noise may still land, and it doesn't repeat, where real allocation does, so a measure that isn't clean is taken again and the cleanest stands. A leak fails every attempt.
